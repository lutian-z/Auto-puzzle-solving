# 扫雷项目交接说明

自动完成 cn.puzzle-minesweeper.com 逻辑题：识别原题 → 唯一解求雷 → 右键插旗 → 回读校验后回车提交。

## 目录结构（2026-09-22 整理后）

```
main.py                 主流程 + CONFIG(三层配置最内层)
ms_solver.py            MILP 精确求解(-2=旗按已判雷参与约束)
ms_auto/                自动化包(原 2800 行单文件 ms_auto.py 按职责拆分, 对外接口不变)
  desktop.py            中断热键 / 选题(框选|两点) / 截屏 / 鼠标键盘
  grid.py               隔线检测 / analyze_screen / 滚动偏移 / 顶边锚定
  classify.py           单格分类(未翻开 / 数字含0 / 旗), 颜色+字形判据
  rows.py               StitchedBoard / 行指纹与行证据 / 各场景绝对行号选择
  recognize.py          识别管线: stitch_recognize(滚动拼接) 与 recognize_visible_board(单屏)
  fill.py               回填管线: fill_from_board(滚动) 与 fill_visible_board(框内直点)
regress_check.py        离线回归(无需显示器), 用法: python regress_check.py [截图.png]
ms_auto.py.bak_20260922 拆分前的单文件备份
```

## 不可破坏的安全门（历次实机教训，全部保留）

不完整题面不求解；有 UNKNOWN 不回填；回填数量不一致不提交；识别矛盾不猜；
完成后不滚回页面顶端；框选模式全程零滚轮（回归里有"调 scroll_wheel 即抛错"断言）；
自洽性检查把旗(-2)计入未翻开邻格。

## 2026-09-22 修复：20x20 题被识别成 10x10（用户实机日志驱动）

根因：浏览器小数格距（此题物理 pitch≈46.7px）把**一半网格线反锯齿渲染成
跨两行的中灰双线**（像素值约 134/146-159）。旧检测 `DARK_GRAY=130` 只看到
隔一条的实线（102），网格减半，格内数字错乱，产出 6 个假"矛盾数字"。

修复（`grid.py`）：新增"柔化线二次细分"——analyze_screen 在算出初步 pitch 后，
检查每对相邻检测线的中点：中点 ±4px 窗口内若存在"横贯棋盘 ≥75% 宽度、像素值
<180"的线（逐像素占比判据，对数字笔画/浮雕阴影鲁棒），过半间隔命中则把中线
补进带列表、格距减半；横竖各自独立判定，裁剪后重检列线时同样补一次。
正常整数格距/小格距（pitch<32）不触发，幂等。

验证（regress_check.py，13 项全过）：用户截图网格=20x20、逐格与原题一致、
自洽 0 矛盾、唯一解 0 未知、框选端到端(桩截屏)回填 96 雷坐标逐格正确、
平移/增亮扰动逐格一致、合成棋盘无误细分。

## 2026-09-22 二次修复：50x50 小格距完全识别不到（"框内未检测到棋盘网格"）

根因(同族问题更极端形态)：格距≈23px 时**所有**内部网格线被反锯齿摊到
134~230 灰度（无任何一条过 180/130 阈值），逐线检测只剩两条边框。且本站
**翻开格与未翻开格格体同为 204 灰**，唯一区分是未翻开格贴线内侧的 1px 浮雕
高光——固定 2px 内缩裁切在高光恰被切掉时把未翻开格整片读成 0。

修复（grid.py + classify.py + rows.py）：
1. 全柔化兜底通道 `_synthesize_grid_rescue`：检测带过少/过疏(细分后间距仍
   >1.55×自相关周期)时，用行/列中位数剖面的自相关定周期，以检出边框为锚
   合成等距线列，逐线"相对暗谷≥12"验证(93%) + 半周期错位对照(≤40%) + 方形
   一致性 + 检出带落格校验，任一不满足即放弃并维持原失败（绝不猜网格）。
   合成线再 `_snap_lines_to_valleys` 吸附到 ±3px 内最暗行，消除小数布局的
   逐线累积相位差。
2. 小格距(<30px)裁切改为"左上缩 1px、右下不缩"(classify_screen 与
   _row_values_at 同步)：保住 1px 浮雕高光进 bright_ratio 判据窗。
   实测分开完全清晰：未翻开 0.08~0.10 vs 翻开 0.000（阈值 0.06）。

验证（regress_check.py 现 26 项，两图端到端）：50x50 识别 n=50、自洽 0 矛盾、
唯一解 0 未知(678 雷)、框选管线无滚动、回填坐标逐格正确、扰动逐格一致、
全柔化合成兜底不误触发；20x20 用例全部维持通过。

## 2026-09-22 三次修复（实机 pitch≈21.5px 时残留 16 个矛盾）

用户实机第二次运行仍报 16 个"数字>周围未翻开"矛盾——全部是"未翻开格被
读成翻开"方向、每次差 1。原因: 之前离线验证用的是用户 23px 格距的截图，
本次实机窗口更小(格距≈21.5px, 且 DPR 缩放下浏览器线更锐、1px 高光更容易
整条落到 235 阈值外/被线 AA 吞掉)。修复三层：
1. 小格距(<30px)切格改为不缩(线行并入格窗)，1px 高光可能落在网格线行本身。
2. 未翻开新增"结构判据"：紧贴上线/左线的 3 行×列带内, 每列(行)存在比
   格体中位数亮 ≥18 灰阶(下限 222)的亮像素且覆盖 60% —— 相对亮度, 不依赖
   绝对阈值与 ±1px 相位。翻开格贴线处只有暗线 AA, 不会两侧同时点亮。
3. 框选识别加自适应救援：小格距且自洽检查有矛盾时, 放宽一档结构判据
   (亮差≥10/下限214/带4/覆盖50%)重分类一次, 矛盾严格减少才采用, 否则维持
   安全终止。只会救回, 不会放行错答。

后续(同日晚, 用户真实 21.5px 截屏回灌后终版)：
- 该截屏连网格都没过——整数滞后自相关在 21.48px 这类小数格距下失效
  (lag21/22 各差半像素, 千余像素跨度去相关, 只剩 43 的倍频假峰)。已改为
  `_best_axis_pitch`: 真实网格两端必在边框上 => 格数 k 必为整数, 直接按
  k 从细到粗扫 linspace(a,b,k+1) + 逐线暗谷验证 + 半格错位对照, 精确处理
  任意小数周期(实测 21.48 一次命中 50)。
- 结构判据终版: 带窗放宽到 6px(容忍网格相位 ~4px 漂移), 判据从"逐列取
  max"改为"带内存在一条横带, ≥55% 的列像素 ≥ max(body+10, 216)"(竖带同理)
  ——真浮雕是贯穿整格的亮线, 邻格渗入/线 AA 只点亮局部列。
- 终版实测: 21.5px 真实截屏识别 50×50、与 23px 已验证棋盘逐格 0 差异、
  唯一解 0 未知 678 雷; 20x20/50x50(23px) 不回退; regress_check.py 现
  支持多张截图参数, 3 图 32 项全过。

已知局限更新：小格距图强增亮(≥1.15×)时高光线饱和可能伪装成浮雕亮边(实测
6 格误报未翻开)——真实屏幕亮度不变时不触发。整屏重度变暗(≤0.92)时, 分类器
绝对高光阈值(>235)会把未翻开格读成 0, 属"静默错读格值", 但会被自洽性安全网
拦下(回归断言: 矛盾数>0), 不会错答提交。实机屏幕亮度正常, 两者都不受影响;
小格距实机形态最终以用户真实截屏验证, 复现工具=regress_check.py + 截图。

补充(同日第四修 → 尺度无关化重构, 用户驳回"分大小格距"的设计): 40x40
格27px 报"6 周围未翻开不足"——起因正是分档开关不同源(切格 pitch<30, 结构
判据 h≤26, 27px 踩缝)。第一反应给 min(h,w)≤30 打补丁被用户否决, 遂重构:

- 切格: classify_screen / _row_values_at 一律整格切片(线行并入), 数字墨迹
  由 _ink_mask 的 12% 比例边距避开贴线 AA——全流程无 pitch 分支。
- 未翻开判据(cell_is_unopened)全部为比例/相对定义, 任何格距同一条路径:
  1) 全格高光占比 >6%(比例判据, 大格距/提亮形态);
  2) 结构判据: 格体基线 = 中心区**众数**(中位数会被大号 0/8 笔画拉低,
     阈值崩塌致翻开格误判未翻开——重构中实测踩到, 已入回归), 阈值 =
     max(众数+10, 216); 带窗 = 格边长/3(限 4~10px, 容忍渲染相位漂移);
     贴上线/左线的带窗内存在横贯/纵贯 ≥55% 的亮带即为浮雕。
- 高光救援(放宽二次分类)去掉 pitch 闸, 任何格距有矛盾即可尝试。
- 绝对像素数只保留在"该尺寸根本无法作答"的可行性边界(RESCUE_MIN/MAX_PITCH,
  SOFT_SPLIT_MIN_PITCH), 不属于识别分档。
- 验收: 4 张真实截图(47/23/21.5/27px)与各自已验证棋盘逐格 0 差异, 全部
  唯一解且解满足约束; 41 项回归全过。

设计准则(防再犯): **凡判据, 只用比例/相对量; 绝对像素数只允许出现在
可行性兜底里。描述同一概念的两个阈值必须同源。**

## 回填提速（2026-09-22，借鉴马赛克项目实测结论）

剖析(50x50/678雷)：回填时间大头不是点击本身——①每行点击前的
`_grab_analyze` 会整屏 analyze_screen 一次(~110ms, 小格距走救援通道更甚)
而结果被丢弃(坐标全用识别期网格) → 改为只 `grab_screen`；②pyautogui 单次
click 封装开销 10~20ms → Windows 走 ctypes SetCursorPos+SendInput 右键
快速路径(<0.5ms, 非 Windows/异常自动回退 pyautogui)；③Windows 默认定时器
粒度 15.6ms, sleep(0.015) 实际睡 16~31ms → 快速路径初始化时
timeBeginPeriod(1)，click_interval 默认 0.015→0.006。
预计 678 雷回填从 ~30s 降到 ~6s。安全网未动：每行点击前仍重新截屏逐行
校验、数量不符不提交。若某台机器出现漏旗，把 main.py CONFIG 的
click_interval 调大(如 0.01)即可，无需改代码。

## 历史结论速查

框选=独立单屏管线(框=完整题目, 底由框定义, 不判边框粗细); 两点点击=滚动拼接;
滚动回填主定位=数字内容匹配(像素位移仅预测), 点击前逐行三态校验 ok/continue/fatal;
旗子分布定位有固有歧义已放弃; 顶边锚定=左边框长暗带起点+加粗候选复检(细线/虚线稳健)。
